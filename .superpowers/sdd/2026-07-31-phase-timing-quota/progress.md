## 分支做了什么（一句话）

`runPhaseWithTimeout` 的三个超时返回点改为按**已发放的配额**计账（`Math.max(elapsedMs, timeoutMs)`），把「预算是否耗尽」从**墙钟测量**变成**超时触发的后果**。

**依据**：`getPhaseTimeoutMs` 本就是 `min(perAttemptTimeoutMs, timeRemainingMs)`。当预算是较小的那个操作数，**超时触发即意味着预算按定义已耗尽**，不该回头拿墙钟去重新推导。当 `perAttemptTimeoutMs` 是较小操作数时，`Math.max` 的下限低于剩余预算，**不会强制任何东西耗尽**。

**它取代了什么**：handoff 曾把「`Date.now()` → `performance.now()`」记为「唯一能真正消除该家族的手段」。**那句话是错的**——换时钟只是把余量从 0 放宽到约 +0.39ms，时钟仍留在判定里。本分支把时钟从判定里拿掉。

## 缺陷的形状：只有一种

上面十几条缺陷里，绝大多数是**同一个形状**：

> 写下一个数字 → 同一波里更晚的编辑把它作废 → 没有人回头重推。

具体案例（全部实测，可自查）：

- `9e554ce` 的提交信息说位移是「+8 / +19」。实际那时已是 +19/+19——它漏了**实施者自己后一笔** `ea271d6` 在同一区域加的 11 行。
- 修复波 2 补上 `ea271d6` 之后写成「+19 / +38」。实际那时已是 +24/+43——它漏了**它自己第三笔** `6b39697` 加的 5 行。**同一个错误，连犯两次，两次都是自己作废自己。**
- 修复波 3 在 `docs/+src/+tests/` 用三桶分类（顶掉 / 位移为 0 仍有效 / 起点即错），换到 `.superpowers/` 就塌成两桶，第三桶唯一的成员被误塞进「起点即错」，12 写成 13。
- 修复波 4（控制器）在论证「锚点必须唯一」的那句话里，把「2 个命中属另一个函数」写成了 1 个。
- 一条重推命令用 `$(git merge-base HEAD main)` 作起点：本分支一旦并入 `main`，它解析成 HEAD 自己、**返回空且退出 0**，读者会读成「没有位移」而不是看到报错。Rule 12 的反面教材。
- 一条重推命令的模式末尾带 `(`：本仓库的 `grep` 被改写成正则引擎，**报错退出 2**，读者照做只会看到 `unclosed group`。必须 `-F`。

**唯一没出错的数字，是唯一附了重推命令的那个**（`runLoop.ts` 超时注释里的 10/49）。于是立了规矩：**文档里每一处算出来的行号 / 位移 / 计数，旁边必须就地附一条能重推它的命令**，见 handoff 遗留事项 8。

## 引用清扫的归属判据（本轮确立）

判据只有一个：**该引用在 merge-base `07180a7` 上是否本来就有效**。

- 有效而被本分支顶掉 → 改，且改成**符号锚点**，不重新编号（没有编译 / 测试 / lint 会检查行号，而 grep 找得到符号）
- 起点就已经错 → **不动**（属更早的层，动它违反 Rule 3）
- 位移为 0 且仍有效 → 不动，但**必须单独成桶**，否则会被误记进「起点即错」

`docs/+src/+tests/`：44 条引用 = 15 顶掉 / 2 位移为 0 / 27 起点即错。
`.superpowers/sdd/`：23 条 + 2 处裸续接 = 10 顶掉 + 2 裸续接 / 1 位移为 0 / 12 起点即错。**这 23 条按不可改写的历史过程记录处理，刻意一条未动**——与 handoff 对 `9e554ce` 提交信息的处理同一立场：就地勘误，不改原件。

⚠️ **44 / 15 / 2 / 27 这四个数至今未被任何一轮独立复核**（修复波 3 与第五、六轮评审都明确声明没有重数）。**要用它们，先自己重数。** 另注意 44 数的是**引用条数**（一个 `:864-866` 区间、一串裸续接各算一条），不是 grep 出现次数（`07180a7` 上 53 次、HEAD 上 29 次）。

⚠️ **正则看不见的一类**：本仓库惯例是写完全路径后用裸 `:NNN` 续接（`:747`、`:958-959`）。`runLoop\.ts:[0-9]+` 扫不到它们，但它们和主引用同属一个主张、同样失效。

**结构性发现**：27 条「起点即错」里绝大多数集中在 plan 文件的 `**Files:** - Modify: <path>:<lines>` 条目上——那是**写计划时**的文件状态，实现落地后必然失效。这不是偶发漂移。**留给 L3 定性**：要么规定 plan 不写行号，要么明确 plan 里的行号是历史快照、不承诺现行有效。

## flake (F) 的定性过程（方法本身值得记）

`runLoop.integration.test.ts > continues normally when execute returns a complete result during the recovery window`

**交接给的配方是「双臂各 50–100 次隔离跑」。照做并加倍（各 200 次）之后，双臂全 0。** 隔离把并行负载拿掉了，而这条失败只在负载下出现——**那个配方对这条失败是错的条件，是它自己证伪了自己。**

改用全套件重复跑（双臂各 100 次）才拿到结果：本分支 0/100，`main` **1/100**。

结论与两个不能顺手下的结论，见 handoff 遗留事项 2 (F)。此处只记方法教训：

- **对抗条件要按失败的机制选，不能按习惯选。** 刀尖家族（(A)）是空闲危险、负载安全；(F) 正好相反。同一个仓库里两种方向相反的计时失败并存。
- **0/100 vs 1/100 分辨不出任何东西**（Fisher p≈1）。样本量不够时，两个方向都能骗人——最初那次「分支 1/12、base 0/12」指的方向就是反的。
- **机制仍是假说**：并行争 CPU 把某相位真实墙钟顶过 5000ms 总预算。只有一个失败样本、未捕获 `budgetSnapshot`。**别写成已证实。**
