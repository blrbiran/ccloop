### 1.3 「删而不是改写」这个选择成不成立

实施者的理由（task-1-report.md:493-497）：能描述准回调体的说法对论证毫无用处，
支点是「谁能修好它」而非「回调格式化多少」；留着只会再给下一位读者一个可拿去校核实现的把手；
删后退回的两项（不碰文件系统、不 await）今天为真，且是「它抛出不可能是环境事实」所需的全部前提。

**独立核实这两项今天是否为真**（读源码，不采信报告转述）：

```
$ sed -n '205,210p' src/sweep/sweepRuns.ts
        onReconciliationWriteAbandoned: (detail) => {
          options.stderr(
            `note  ${candidate.path}  reconciliation_write_abandoned  ${detail.replace(/\r?\n/g, " ")}`,
          );
        },
      });
```

回调体确实只做一件事：同步调用 `options.stderr(...)`。函数体内没有 `fs`/`fsPromises` 调用、
没有 `await`、没有异步操作——「不碰文件系统、不 await」两项今天为真，独立确认成立。

**再判论证支点是否还撑得住结论**：`spec:759` 这段的结论是
「回调抛出只可能是调用方的编程错误，必须显眼炸出来」，支点写明是「谁能修好它」——
`options.stderr` 是调用方（`SweepOptions.stderr`）注入的槽，回调只是同步调用它一次、不碰文件系统、
不 await，也就是说回调体的全部行为都在**本层的控制范围内**（没有把控制权交给任何回调之外、
本层管不到的子系统）。这个「控制范围」判断只依赖「同步」＋「不碰文件系统」＋「不 await」三点，
与回调内部拼装了几段字符串、折不折行**完全正交**——格式化逻辑本身既不产生 I/O、也不产生异步
让渡，不改变「控制权留在本层」这个事实。所以删掉「不格式化超出一次折行」之后，
论证链条（同步调用注入槽 → 控制权在本层 → 抛出只能是编程错误 → 必须炸出来）**一步都没有缺失**，
结论依旧撑得住。

**这个理由是否有反面**：唯一值得警惕的反面是——如果读者需要知道回调「具体做什么」来判断
它是否可能因格式化逻辑本身抛出异常（例如 `String(undefined)` 之类的边缘情况），删掉这句话
会不会削弱论证？答案是不会：论证从未依赖「格式化逻辑不会抛异常」，它依赖的是「万一抛出，
责任在调用方」，这是纯粹的控制权归属论证，不是「回调不会出错」的论证。因此这处反面不成立。

**结论：删而不是改写，这个选择站得住。** 这不是偷懒式的规避，而是精确识别出被删的半句
对论证毫无支撑作用（reviewer 自己也在 review-task1.md:412-414 给出了同样的修法），
且删除后不留下会引诱下一位读者去核对实现细节、却与论证本身无关的「假把手」。
